## 1. Executive Purpose

This document is the controlling verification model for the FathersNet (Ayay) build. It answers one question at every gate and phase exit: **what artifact proves this is done, who produced it, and who signed it.**

The roadmap in `14` defines eleven verifiable delivery units (Phase 0–Phase 10), each with objectives, acceptance criteria, and a Verification Evidence list. This plan operationalizes that list into a single, consistent, evidence-driven system:

| Property | Value | SRS Anchor |
| --- | --- | --- |
| Every phase exit requires artifacts | A phase is complete only when its named evidence artifacts exist, pass, and are signed. Narrative demos and verbal assertions are not evidence. | `14` §3–§13 Verification Evidence; QR-013; QR-015 |
| Every component is verifiable independently | Authentication, user/profile, pregnancy engine, reminders, WhatsApp, AI/RAG, content/CMS, mobile, admin, research, campaigns each have a defined evidence bundle. | §17.2/17.3/17.4; `13` §3–§11 |
| Cross-cutting controls are verified in every phase | Security, privacy, localization, observability, idempotency, auditability are never "verified later"; they carry per-phase evidence from Phase 1 onward. | `14` §2.3; `02` §5 |
| QR gates carry fixed evidence bundles | QR-013 (release gate), QR-016 (release review), QR-017 (UAT), QR-018 (pilot evaluation) each have a named bundle in Section 7. | §17.1 |
| Evidence is retained and traceable | All artifacts are stored per a fixed naming/location scheme (Section 9) and linked to requirement IDs for QR-015. | QR-015; §18.1 |
| Sign-off is accountable | Every phase has a named approver matrix (Section 10); a gate is not closed without the required signatures. | `14` §15 milestones; Appendix E |

**Source:** SRS §17.1 QR-013, QR-015, QR-016, QR-017, QR-018; §18; `14` §18. **Classification:** Confirmed. **Confidence:** High. **Reasoning:** QR-013 makes release conditional on combined passing test/scan/clinical evidence; QR-015 makes traceability mandatory; `14` already names Verification Evidence per phase, which this plan standardizes. **Impact if changed:** If the SRS relaxes or adds a QR, this document's evidence bundles in Sections 4 and 7 must be re-derived from §17.1 before the next gate.

## 2. Verification Model

### 2.1 Evidence-Driven Completion Rule

**Confirmed.** No implementation claim is accepted without an artifact. The verification model binds every acceptance criterion in `14` and every QR to a stored evidence artifact.

**The rule:** A phase or component is **Verified** only when all three conditions hold:

1. **Produced** — the evidence artifact exists at the path assigned in Section 9 and was generated by the named tool/process in Section 8.
2. **Passed** — the artifact shows the required result (green suite, zero critical/high findings, measured values meeting targets, or a signed human review).
3. **Signed** — the approver named in Section 10 has recorded sign-off, referencing the artifact path and requirement IDs.

If any condition fails, the phase/component is **In Verification** (SRS status definition, §1.7), not complete. This is the formal meaning of "In Verification" used throughout the program.

**Source:** SRS §1.7 status definitions; QR-013; QR-015; `14` §18. **Classification:** Confirmed. **Confidence:** High. **Reasoning:** QR-013 and QR-015 cannot be satisfied by narrative; only stored test/scan/review artifacts can prove coverage and status. **Impact if changed:** Relaxing the rule to accept verbal sign-off voids QR-013's guarantee and makes the release gate unauditable.

### 2.2 Verification Layers

Verification is performed at four nested layers. Every artifact belongs to exactly one layer:

| Layer | Scope | Artifact Owner | Evidence From |
| --- | --- | --- | --- |
| **L1 Continuous** | Every PR/merge in CI: lint, unit tests, coverage floor, SAST, dependency scan, secret scan, contract checks | Engineering + QA via CI | CI job logs and reports (Section 8 tooling) |
| **L2 Phase exit** | Each Phase 0–10 acceptance criterion from `14` | Phase owner (Section 10 approver) | Phase evidence pack (Section 4) |
| **L3 Component** | Each major component's functional + non-functional proof | Component owner + QA | Component evidence bundle (Section 5) |
| **L4 Program gate** | QR-013/QR-016/QR-017/QR-018 release and pilot gates | QA Lead + Program leadership | Gate evidence bundles (Section 7) |

**Source:** QR-001 layered test strategy; `14` gates G1–G3; `13` §15 gates G0–G10. **Classification:** Confirmed (structure); Recommended (layer naming). **Confidence:** High. **Impact if changed:** Collapsing layers removes the ability to attribute a gate failure to its source (a bad PR vs. an incomplete phase vs. a gate condition).

### 2.3 The Evidence Lifecycle

1. **Plan:** At phase kickoff, the phase owner copies the required evidence list from Section 4 into the phase backlog with owners and due dates.
2. **Produce:** Evidence is generated by the tooling in Section 8 against versioned environments and fixtures (QR-012).
3. **Register:** Artifacts are stored under the Section 9 registry with the naming convention and linked to requirement IDs in `22-feature-implementation-matrix.md`.
4. **Review:** QA Lead reviews each artifact for validity (correct tool, correct environment, no stale date, no tampered result).
5. **Sign:** The Section 10 approver signs; sign-off is recorded in `implementation-status.md` with artifact paths.
6. **Retain:** Artifacts are retained per Section 9.3 retention classes (§18.1).

**Source:** QR-015; §18.1; `14` §18.7. **Classification:** Confirmed process. **Confidence:** High. **Impact if changed:** Skipping any step (e.g., signing without QA review) re-introduces the "narrative sign-off" failure mode this plan exists to prevent.

### 2.4 Artifact Registry

The artifact registry is the canonical index of all verification evidence. It is maintained in `implementation-status.md` and mirrored as a directory tree under `verification/` (Section 9.1). Each registry entry has exactly these fields:

| Field | Content | Example |
| --- | --- | --- |
| **Artifact ID** | Unique ID per the Section 9 naming scheme | `T-TEST-2026-09-04-08-report.pdf` |
| **Requirement(s)** | Requirement IDs it proves (QR-015) | `FR-063, NFR-046, QR-014` |
| **Phase / Component** | Owning phase and component | Phase 5 · AI/RAG |
| **Evidence type** | One of the 12 types in Section 3 | Test results |
| **Environment** | dev / staging / prod / review | staging |
| **Tool** | Generating tool (Section 8) | pytest + eval harness |
| **Status** | Produced / Passed / Failed / Under review / Signed | Passed |
| **Approver + date** | Sign-off from Section 10 matrix | AI Safety Reviewer, 2026-09-05 |

**Source:** QR-015; `14` §18.7. **Classification:** Confirmed (existence); Recommended (schema). **Confidence:** High. **Impact if changed:** A registry without requirement linkage makes QR-015 unprovable; without environment metadata, stale/misleading artifacts can pass review.

## 3. Required Evidence Types

Twelve evidence types are defined program-wide. For each: **what it is**, **how to produce it**, **who reviews it**, and the SRS authority. Every artifact in the registry is exactly one of these types.

### 3.1 Screenshots (mobile screens, admin dashboards, WhatsApp conversation captures)

| Attribute | Content |
| --- | --- |
| **What it is** | Timestamped captures proving UI/UX, role-based views, localization rendering, offline behavior, accessibility states, WhatsApp flow outcomes, and dashboard content. Used to prove visual/behavioral claims that tests cannot. |
| **How to produce it** | Device-matrix runs (low-end/mid Android, iOS, TalkBack/VoiceOver on) and admin-role sessions against staging, each capture annotated with environment, user/role, locale, and scenario ID. WhatsApp captures taken from the provider sandbox or mocked client. Captures stored as PNG with a companion annotation file (scenario, expected vs. actual). |
| **Who reviews** | QA Lead verifies the capture matches the scenario and environment; Product/UX owner confirms visual correctness; accessibility reviewer confirms assistive-tech states (Phase 6/7). |
| **Authority** | §17.4 (device matrix, dashboard role tests); NFR-030…NFR-033; FR-134 (low-literacy UX), FR-141 (assistive tech), FR-140 (WCAG). |
| **Confidence** | High (requirement); Medium (capture methodology). |
| **Reasoning** | Screenshots are the only artifact that can prove rendering, locale completeness, and accessibility states for a low-literacy, Amharic-first audience. |
| **Impact if changed** | If screenshots are replaced by test-only assertions, visual/localization/accessibility regressions escape to UAT (QR-017). |

## 10. Sign-off Workflow

### 10.1 Sign-off Rule

A phase or gate is signed only when: (1) the QA Lead has reviewed the evidence pack for validity (correct tool/environment/date, no failures hidden), (2) the phase owner confirms all acceptance criteria from `14` are met, and (3) the approver(s) in the matrix below sign referencing artifact paths. Sign-offs are recorded in `implementation-status.md` and linked to the artifact registry. **Source:** `14` §15 (milestone evidence owners), §18; QR-013/015. **Classification:** Confirmed. **Confidence:** High. **Impact if changed:** Allowing sign-off without QA review reintroduces the narrative-closure failure this plan eliminates.
